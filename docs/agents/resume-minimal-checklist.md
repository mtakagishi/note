# 作業再開の最小チェックリスト

## 目的

トークン消費を抑えながら、前回作業の続きに安全に再開する。

## 原則

- まずは最小確認で開始し、必要条件を満たした場合のみ全履歴確認に拡張する。
- 再開時の確認範囲は、Issue 1件、最新マージPR 1件、現在ブランチの3点を起点にする。
- 公開承認は人間だけが行い、再開時の半自動化は公開可否を決定しない。

## 半自動化の境界（中レベル）

- 自動化してよい対象は、状態収集、差分有無確認、次の一手の提案までとする。
- 自動化しない対象は、議題種別の暗黙決定、公開承認、恒久方針の採用とする。
- 必須情報欠落、正本不一致、議題不一致がある場合は処理を停止し、人間確認へ切り替える。

## 半自動化I/O契約（最小確認）

- 入力:
  - 議題種別（①優良記事作成 / ②方法論改善）
  - 起点ファイル（`_notes/sessions/resume-handoff-latest.md`）
  - 参照範囲（現在ブランチ、open issue、最新 merged PR、main差分、最新`DECISIONS.md`）
- 出力:
  - 確認結果5点（ブランチと作業ツリー、open issue、最新 merged PR、main差分、採用済み判断整合）
  - 不一致または不足の有無
  - 次の最初の作業1件（提案）
- 停止条件:
  - 議題種別が宣言されていない
  - 起点ファイルの必須項目（議題種別、起点issue、次の一手）が欠落している
  - Issue、最新HANDOFF、`STATUS.md`、`DECISIONS.md`の間で矛盾がある
  - 公開可否や恒久方針に関わる判断を自動で確定しようとしている

## 最小確認手順（標準）

1. 議題種別を「①優良記事作成」または「②方法論改善」のどちらか一つで宣言する。
2. 前提チェックとして、`_notes/sessions/resume-handoff-latest.md`の議題種別、起点issue、次の一手を確認する。
3. 機械実行として、現在ブランチと作業ツリー状態を確認する。
4. 機械実行として、open issue 一覧を確認し、今回の起点 issue を1件に絞る。
5. 機械実行として、最新の merged PR を1件確認し、次に触る境界を特定する。
6. 機械実行として、main の先頭コミットと現在ブランチの差分有無だけ確認する。
7. 機械実行として、最新の`DECISIONS.md`を確認し、採用済み判断が今回の議題種別と矛盾しないかを確認する。
8. 最終人間確認として、誤公開防止の境界を維持したまま次の一手を1件だけ確定する。

上記で判断できる場合は、ここで再開してよい。

## 全履歴確認に拡張する条件

次のいずれかに該当する場合のみ、PR/Issue 全履歴を再確認する。

- 直近で複数の並行ブランチが同じファイル群を変更している。
- 起点 issue と最新 PR の関係が不明確で、要件の連続性が読めない。
- 失敗した CI やコンフリクト解消履歴を追わないと判断できない。
- 途中で命名規則や運用ルールが更新され、適用境界が不明になっている。

## セッション終了時の記録テンプレート

次回再開を軽くするため、作業終了時に次の8項目を残す。

1. 今回の議題種別（①優良記事作成 / ②方法論改善）
2. 起点 issue 番号
3. 最終 merged PR 番号
4. 次に着手する作業名（1行）
5. 記事側の残課題（最大3件）
6. 方法論側の残課題（最大3件）
7. 触る予定の主ファイル（最大3件）
8. 再開コマンド（確認用コマンド群）

同一セッションで①と②が混在した場合は、残課題を分割記載し、次回は片方だけを再開対象にする。

記録先は `_notes/sessions/resume-handoff-latest.md` を使い、毎回上書き更新する。

## 再開時に使うプロンプト

次回は、次のプロンプトを貼って再開する。

### 最小確認版（通常はこちら）

```text
_notes/sessions/resume-handoff-latest.md を起点に、最小確認手順で再開してください。
最初に議題種別を「①優良記事作成」または「②方法論改善」のどちらか一つで宣言してください。
確認は以下だけに限定してください。
1) 現在ブランチと作業ツリー
2) open issue
3) 最新 merged PR
4) main との差分有無
5) DECISIONS.md の最新採用判断

判断に不足がある場合のみ、全履歴確認に拡張してください。
確認結果を日本語で要約し、次の最初の作業を1つ提案してください。
```

### 拡張確認版（必要時のみ）

```text
_notes/sessions/resume-handoff-latest.md を起点に再開してください。
今回は拡張確認が必要です。Issue/PR の履歴を遡り、要件の連続性、衝突リスク、未解決事項を確認してください。
最初に議題種別を「①優良記事作成」または「②方法論改善」のどちらか一つで宣言し、混在している場合は分割案を先に提示してください。
結果を日本語で、
1) 現在地
2) リスク
3) 次に着手すべき作業
の順で簡潔にまとめてください。
```

## ループモード再開（時間指定）

初回再開後、継続的に作業を進める場合に使う。一定時間内で複数の「次の一手」を自動で実行するパターン。

### 使用場面

- 方法論改善の多数タスク（ドキュメント更新、テスト実装、プロセス定義など）を連続実行したい
- 記事作成の連鎖作業（キャプチャ→承認→検証→公開）を時間制約内に収めたい
- 時間ブロック（例：15分、30分）内で「次の一手」を可能な限り消化したい

### ループモード再開プロンプト例

```text
ループモードで再開します。N分間、以下を自動で繰り返してください。

1. STATUS.md または resume-handoff-latest.md の「次の一手」を確認する
2. その作業を実装・検証する（ファイル編集、テスト実行、確認など）
3. 必要に応じてファイルを更新し、コミット・プッシュする
4. コミット完了後、STATUS.md の「次の一手」を新しいタスクに更新する
5. 1～4 を繰り返す

終了条件:
- N分経過したとき、そこまでで停止する
- 停止すべき判断が発生したとき（矛盾検出、データ不足など）は即座に停止する

完了時は、以下をレポートしてください:
- 実行時間（開始～終了）
- 完了したコミット（全件、1行ずつ）
- 各コミットの1行サマリー（1コミット1行）
- 次に着手すべき作業1件（次の再開時プロンプト用）
```

### ループ中の記録・コミット指針

- **必ず行う**:
  - 各タスク完了後にコミット・プッシュする
  - STATUS.md の「次の一手」を更新する
  - resume-handoff-latest.md の「次に着手する作業」を新タスクで更新する
- **必ず停止する**:
  - 必須情報欠落（次の一手が定義されていない、判断基準が不明など）
  - データ矛盾（Issue/PR/ブランチ間の要件不一致）
  - 意思決定が必要な判断（複数案の優先順位、公開可否など）
- **ループ外で確認する**（ループ中は実行しない）:
  - 最小確認手順（git、gh コマンド実行）— 最初の1回だけ実行し、以後は STATUS.md から判断
  - 公開承認、恒久方針採用 — 人間判断へ委譲

### ループ完了時のレポート形式

```
## ループ実行完了レポート (2026-MM-DD HH:MM～HH:MM JST, N分間)

完了コミット:
- abc1234: docs: update ...
- def5678: test: add ...
- ghi9012: notes: record ...

次に着手すべき作業:
- [内容]

停止理由（あれば）:
- なし / あり（理由: ...）
```

## 再開コマンドの最小セット例

- git status --short --branch
- gh issue list --state open --limit 20
- gh pr list --state merged --limit 5
- git log --oneline --decorate -n 10

## 半自動化用コマンドテンプレート（確認専用）

次のコマンドは、最小確認の「機械実行」だけをまとめて実行するための確認用テンプレートである。公開承認や恒久方針採用は行わない。

```powershell
git status --short --branch
gh issue list --state open --limit 20
gh pr list --state merged --limit 5
git rev-list --left-right --count main...HEAD
git branch --show-current
```

実行結果に不一致や不足がある場合は停止し、手動で最小確認手順の前提チェックへ戻る。

## 実行ログの記録形式（半自動化）

半自動化の機械実行を使った場合は、次の5項目を必ず同時に記録する。

1. 実行時刻（JST）
2. 議題種別（①優良記事作成 / ②方法論改善）
3. 確認結果5点（ブランチと作業ツリー、open issue、最新 merged PR、main差分、`DECISIONS.md`整合）
4. 停止有無（停止理由、再開条件）
5. 次の最初の作業（1件）

記録先は、`_notes/sessions/resume-handoff-latest.md`の「次に着手する作業」「方法論側の残課題」を更新して同期する。

```markdown
## RESUME CHECK LOG YYYY-MM-DD HH:MM JST

- 議題種別: ① / ②
- 実行時刻: YYYY-MM-DD HH:MM JST
- 確認結果:
  - ブランチと作業ツリー: ...
  - open issue: ...
  - 最新 merged PR: ...
  - main差分: ...
  - DECISIONS整合: ...
- 停止有無: なし / あり（理由: ...）
- 再開条件: ...
- 次の最初の作業: ...
```

### 3回試行の記録要約（2026-08-13）

- 議題種別: ②方法論改善
- ブランチと作業ツリー: `agent/implement-feedback-application`でクリーン
- open issue: #2のみ
- 最新 merged PR: #27
- main差分: `0 19`（main側先行0、作業ブランチ側先行19）
- DECISIONS整合: 矛盾なし
- 停止有無: なし

### 記入揺れの補正ルール

1. 時刻は必ず`YYYY-MM-DD HH:MM JST`で記録し、秒は省略する。
2. main差分は`left-right-count`の生値だけでなく、意味を併記する。
3. ブランチ状態は`ブランチ名`と`dirty/clean`の2要素に正規化する。
4. open issueは件数だけでなく、起点issue番号を必ず1件明記する。
5. 最新 merged PRは番号とタイトル先頭のみを記録し、長い枝名は省略する。
6. 停止有無が「なし」の場合も`再開条件: 不要`を明記する。

### 記録責務の分離

- 再開時は、このファイルの実行ログ形式を使って確認結果と次の一手を記録する
- 終了時は、Issue #2のHANDOFFコメントへ要約を転記する
- 再開時の記録は再開判断の証跡、終了時の記録は引き継ぎの正本として扱う
- 1回の再開確認で得た要約は、終了時のHANDOFFへ再利用してよい

## 運用メモ

- 進行中の論点は1 issue に集約し、論点分岐は issue コメントで管理する。
- PR タイトルに工程番号を含めると、再開時の読み直しが短くなる。
- 終了時テンプレートを更新しておくと、次回は最小確認だけで再開しやすい。
- 再開プロンプトは本ファイルの「再開時に使うプロンプト」を正本として扱う。
